### ① 배포 환경에서 AI 추론 비활성화 가능성

[railway_wsgi.py](C:/ygy/KSL_project/backend/railway_wsgi.py:4)에서 `DISABLE_VISION=1`을 설정하고 있습니다. 이 상태에서는 NumPy, OpenCV, MediaPipe뿐 아니라 PyTorch까지 비활성화되어 `/api/predict*`가 503을 반환할 수 있습니다.

게다가 `railway.json`(`python backend/app.py`), `railpack.json`/루트·백엔드 `Procfile`(`gunicorn ... railway_wsgi:app`)의 실행 명령도 서로 다릅니다. **[추가]** 이 세 곳 중 어떤 게 실제로 우선 적용되는지가 Railway 빌더 설정에 따라 달라서, 운이 나쁘면 Flask 개발 서버(`app.py`)가 그대로 운영에 뜰 수 있습니다 — 개발 서버는 단일 스레드라 동시접속 시 응답이 막힙니다.

해야 할 작업:

- 배포 진입점을 하나로 통일 (`railway.json`, `railpack.json`, `Procfile` 2개 중 불필요한 것 삭제)

- `/api/health`에서 단순 서버 생존뿐 아니라 모델 로딩 상태도 검사
- 실제 Railway 환경에서 샘플 영상 E2E 테스트

좋은 트러블슈팅 소재:

> 배포는 성공했지만 추론 API가 503을 반환 → 배포 진입점에서 AI 의존성을 비활성화한 것이 원인 → readiness health check와 모델 로딩 상태 분리

## 2. 시제품 품질을 위해 필요한 작업

### AI 추론 신뢰성

현재 정확도 숫자만으로는 실제 시제품 신뢰도를 충분히 설명하기 어렵습니다.

**[추가] 모델 적용 범위 명확화**: 현재 모델은 범용 수어 인식이 아니라 "복지카드 분실 신고" 시나리오에 좁게 튜닝되어 있습니다. WORD 모델(3,000 클래스)은 검증 정확도 95.7%지만, 실제 키오스크 데모 흐름(SENTENCE, 시나리오 룩업 기준 약 8~12개 서브셋)에서는 평균 ~87%, 일부 클래스는 40%까지 떨어집니다. 데모 스크립트는 이 시나리오 범위 안에서만 진행해야 인식률이 보장됩니다.

**[추가] 설정값과 실제 코드의 불일치**: `config/web_demo.yaml`에 `confidence_threshold: 0.75`가 정의돼 있지만, 실제로는 `backend/inference/predictor.py`가 상황별로 0.20~0.55의 하드코딩된 임계값을 따로 사용합니다. config 파일을 고쳐도 동작이 바뀌지 않는 상태라 운영 중 튜닝이 어렵습니다. 또한 `scenario_lookup.json`과 `lookup_table.json` 두 파일이 같은 시나리오(약 32개 항목)를 중복 정의하고 있어, 둘 다 있을 때 어느 쪽이 우선하는지 코드에서 한 번 더 확인이 필요합니다.

추가하면 좋은 지표:

- 클래스별 precision, recall, F1
- 사용자 미학습 조건 평가
- 밝기·거리·배경·카메라별 평가
- 평균/95% 추론 지연시간
- 무동작 및 미지원 수어 거절률
- confidence calibration 결과
- 오인식 수정 또는 재시도 UX

특히 "잘못된 결과를 자신 있게 보여주는 문제"를 막아야 합니다.

- 임계값 미달 시 후보 3개 표시
- 사용자가 결과를 선택하거나 수정
- 낮은 신뢰도 로그 수집
- 모델 버전과 예측 결과 함께 기록
- **[추가]** `config/web_demo.yaml`의 threshold 값이 실제로 `predictor.py`에 반영되도록 설정 로딩 경로 통일, `scenario_lookup.json`/`lookup_table.json` 중 하나로 단일화
