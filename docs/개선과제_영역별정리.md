# 개선과제 영역별 정리

> [프로토타입_트러블슈팅_및_개선과제.md](./프로토타입_트러블슈팅_및_개선과제.md)에 정리된 항목을 우선순위(P0/P1/P2)별이 아니라 **담당 영역(백엔드/프론트/서버/DB 등) 기준**으로 재정렬한 버전입니다. 작업 분배·할당 용도로 사용하세요.

> 표시: 🔴 = 시제품 공개 전 필수(P0), 🟡 = 안정적인 데모를 위해 필요(P1), 🟢 = 포트폴리오 완성도(P2)

## 📋 팀 회의 정리 (2026-06)

### 1. 우리의 목표

- 충북데이터 공모전 수상이 목표라기보다는, **3차 프로젝트 전까지 최대한 오류를 잡고 업그레이드**하는 것이 우선
- 6월 28일 공모전은 **"아이디어 기획 부문"**으로 제출

### 2. 담당

| 이름 | 담당 |
|---|---|
| 권오경 | 서류담당 |
| 김동완 | 서버, 백엔드 |
| 윤가연 | 서류보조, 프론트, 백엔드, DB, 서버, 수어통역사 섭외 및 테스트 |
| 최영수 | DB, 프론트, 서버, 수어통역사 섭외 및 테스트 |

### 3. 추가 논의 사항

- **수어통역사 섭외 (2시간 내외)**: 우리가 전문 수어통역사가 아니라서 번역기 정확도를 자체적으로 검증하기 어려움 → 수어를 잘하는 분을 섭외해 직접 테스트하고, 인식 오류가 **프로그램(모델) 문제인지 / 입력된 수어 자체의 문제인지** 구분할 것. → [ML / 추론 파이프라인](#-ml--추론-파이프라인-backendinference-config) 정확도 검증 항목과 연결
- **소켓/서버 구조**: 환자(민원인)가 접수했을 때 상담원(의사) 쪽 화면에 데이터가 보이려면 프론트와 백엔드가 **같은 서버**에 있어야 소켓으로 데이터가 전달됨 — 과거 이 문제 때문에 구조를 바꾼 적이 있었음. 백엔드와 프론트를 함께 호스팅할 수 있는 서버를 구할 수 있는지 검토 필요. → [배포/인프라](#️-배포인프라-railway)의 "프론트 빌드 결과물을 누가 서빙하는지 정의 안 됨" / [시그널링 서버](#-시그널링-서버-nodejs--socketio-server) 배포 이슈와 동일한 맥락

## 🐍 백엔드 (Flask, `backend/`)

- 🔴 `railway_wsgi.py`의 `DISABLE_VISION=1` → 배포 시 AI 추론 전체 비활성화 위험, `/api/predict*` 503 원인
- 🔴 기본 관리자 계정(`admin`/`admin1234`), 고정 Flask secret key → 환경변수 미설정 시 서버 시작 자체를 막아야 함
- 🔴 비밀번호 단순 SHA-256 → Argon2/bcrypt 전환, 로그인 실패 횟수 제한
- 🔴 `/api/predict`, `/api/summary`, `/api/logs` 등 인증 없이 호출 가능 → 인증 정책 + IP/사용자별 rate limit
- 🟡 쿠키 `Secure`/`HttpOnly`/`SameSite`, CSRF 방어, 세션 만료 갱신
- 🟡 `ai_client.py`의 Anthropic 호출에 timeout 없음 → 요청 무한 대기 가능
- 🟡 `print()` 디버그 로그에 예측 결과(상담 내용) 평문 노출 → 구조화 로그 + 마스킹
- 🟢 죽은 진입점 `backend/main.py` 정리
- 🟢 `pyproject.toml`(uv) vs `requirements.txt` 의존성 이원화 → 하나로 통일
- 🟢 `pytest` 도입, 인증/세션/추론/DB API 통합 테스트

## 💻 프론트엔드 (React/Vite, `web/`)

- 🔴 `App.tsx`: 관리자 인증을 `localStorage` 플래그로 판단 → 콘솔에서 우회 가능, 서버 세션 검증으로 전환 필요
- 🔴 `KakaoCallback.tsx`: 카카오 토큰을 `localStorage`에 저장 → XSS에 취약, httpOnly 쿠키 또는 서버 보관 방식으로 변경
- 🔴 `vite.config.ts`: 프록시가 `localhost:5000/5001`로 하드코딩 → 배포 시 `VITE_API_URL`/`VITE_SOCKET_URL` 기반으로 전환
- 🟡 `mediapipeClient.ts`: `?mp=client` 진입 시 미구현 에러로 예측 루프 죽음 → 완성하거나 진입 차단
- 🟡 `useSignLanguage.ts`: 예측 결과를 `console.log`로 그대로 출력 → 상담 내용 노출, 제거 필요
- 🟡 카메라 권한 거부 시 안내 메시지가 부정확("손을 보여주세요"만 뜸) → 에러 종류별 분기
- 🟢 `useSignLanguage.ts` 1,600줄 이상 비대 → 카메라/분절/API/데모 훅으로 분리
- 🟢 Vitest/React Testing Library 도입

## 🔌 시그널링 서버 (Node.js + Socket.IO, `server/`)

- 🔴 `server.js`가 클라이언트가 보낸 `role`(상담원/키오스크)을 그대로 신뢰 → 권한 검사 없음, 누구나 상담원 행세 가능
- 🔴 `server/`에 `Procfile`/`railway.json` 자체가 없음 → Railway에 배포가 안 돼서 영상상담 기능이 운영 환경에서 통째로 실패할 수 있음
- 🟡 Socket 연결 시 JWT/일회용 상담 토큰 검증, 허용 origin 명시, 이벤트 payload 스키마 검증
- 🟡 공개 무료 TURN 계정(openrelayproject)이 `webrtcConfig.ts`·`AgentDashboard.tsx` 두 곳에 중복 하드코딩 → 한 곳으로 통합 + 운영용 TURN 전환
- 🟢 연결 실패 시 재접속/ICE restart UI
- 🟢 Node 테스트 스크립트가 비어있음 → 최소한의 테스트 추가

## 🗄️ DB / 세션 저장

- 🔴 `session/store.py`: 전역 변수 하나에 모든 민원인 정보·메시지 저장 → 동시 접속 시 정보 혼선, 재시작 시 전부 소실. `consultation_id` 기반으로 분리하고 PostgreSQL/Redis로 이전
- 🔴 `db.py`: 암호화 키(`DB_ENCRYPTION_KEY`) 미설정 시 개인정보를 평문으로 저장(fail-open) → 키 없으면 저장 자체를 막는 fail-closed로 전환
- 🟡 세션 만료 시간과 자동 정리(cron/TTL) 없음
- 🟡 개인정보 보존 기간 정책 + 자동 삭제 없음
- 🟢 DB 마이그레이션 도구(Alembic 등) 도입

## 🤖 ML / 추론 파이프라인 (`backend/inference/`, `config/`)

- 🟡 `config/web_demo.yaml`의 `confidence_threshold`가 실제 `predictor.py`에서는 무시되고 별도 하드코딩 값(0.20~0.55) 사용 → 설정 따로 노는 상태, 로딩 경로 통일 필요
- 🟡 `scenario_lookup.json`과 `lookup_table.json`이 같은 데이터를 중복 정의 → 우선순위 불명확, 하나로 합치기
- 🟡 모델은 범용 수어 인식이 아니라 "복지카드 분실 신고" 시나리오 전용(서브셋 평균 ~87%, 최저 40%) → 데모 스크립트를 이 범위로 한정
- 🟢 임계값 미달 시 후보 3개 표시 + 사용자 선택/수정 UX
- 🟢 클래스별 precision/recall/F1, 지연시간(평균/95%), confidence calibration 결과 정리
- 🟢 모델 버전과 예측 결과를 함께 기록(버전 관리)

## ☁️ 배포/인프라 (Railway)

- 🔴 `railway.json`(`python backend/app.py`) vs `railpack.json`/`Procfile`(`gunicorn ... railway_wsgi:app`) 시작 명령 불일치 → 하나로 통일
- 🔴 프론트 빌드 결과물(`web/dist`)을 누가 서빙하는지 정의 안 됨 → Flask 정적 서빙 또는 별도 정적 호스팅 확정
- 🟡 `/api/health`가 서버 생존만 확인, 모델 로딩 상태는 검사 안 함
- 🟢 Git 저장소 pack 크기 ~646MB → 모델 파일 Git LFS로 분리
- 🟢 CI에서 프론트 빌드 + Python lint/type/test 자동 실행 없음
